# fnOS 原生应用部署与统一网关

> 当前 v0.17.0 开发版已完成 Unix Socket、网关 Header、多用户数据隔离和后端 AI 服务基础；FPK、生产静态资源托管及真机统一网关验收仍在 TODO 中。本页打包步骤是下一阶段实施参考，不表示已有可发布安装包。

本文面向需要把 Web 项目部署成飞牛 fnOS 应用的开发者，目标是让第三方项目获得接近系统内置应用的使用体验：

- 通过应用中心安装、启动、停止和升级；
- 在 fnOS 桌面显示应用图标，并可在系统窗口内打开；
- 复用 fnOS 当前域名、HTTP/HTTPS 端口和 FN Connect 入口；
- 复用 NAS 登录态，不再为应用单独实现一套登录页；
- 不为应用额外暴露宿主机 TCP 端口；
- 按需获得当前 fnOS 用户上下文，并继续执行应用自己的业务鉴权。

这里采用官方支持的 **FPK 应用包 + 统一网关 + Unix Socket**。不要修改 fnOS 自带 Nginx、应用中心数据库或影视、相册等官方应用使用的保留路径。

## 版本与工具

统一网关需要 fnOS `1.1.3102` 或更高版本。fnOS 开放 API 还要求系统 `1.2.0401` 或更高版本、飞牛 App `1.34.0` 或更高版本。开放 API 的版本要求不影响统一网关本身的登录校验。

开发和测试主要使用：

- `fnpack`：创建项目并生成 `.fpk`；
- `appcenter-cli`：在 fnOS 设备上安装本地包、启动或停止应用；
- fnOS 应用中心的“手动安装”：适合管理员进行交互式测试。

开始前先查看 [官方更新日志](https://developer.fnnas.com/docs/update-log/) 和 [fnpack 文档](https://developer.fnnas.com/docs/cli/fnpack/)，不要假设设备自带的 `fnpack` 一定是官方文档中的当前版本。

## 选择访问模型

| 模型 | 复用 fnOS 域名和端口 | 校验 NAS 登录态 | WebSocket | 适用场景 |
| --- | --- | --- | --- | --- |
| `index.cgi` | 是 | 调用 CGI 前校验 | 否 | 小型静态页面、兼容简单旧包 |
| 统一网关 | 是 | 转发前校验，并注入用户 Header | 是 | SPA、API、长期服务、流式请求、WebSocket |
| 独立端口 | 否 | 与 NAS 登录态无关 | 是 | 自带完整认证的独立服务 |

现代 Web 项目默认选择统一网关。纯静态页面也可以使用 `index.cgi`，但每次请求都会启动 CGI 进程，复杂 SPA 的路由、缓存和资源回退也更难维护。

## 请求链路

```text
浏览器
  │  https://nas.example/app/myapp/
  ▼
fnOS 主 Web 服务
  │  校验 NAS 会话
  │  注入 X-Trim-* 用户 Header
  ▼
/var/apps/myapp/target/app.sock
  │  Unix Socket 上的 HTTP / WebSocket
  ▼
应用服务
```

统一网关注册公开路径 `/app/myapp`，应用服务监听安装目录中的 `app.sock`。`gatewaySocket` 只填写文件名，Socket 必须由应用创建在安装后的 `target` 目录中。

## FPK 项目结构

普通项目：

```bash
fnpack create myapp
```

Docker 项目：

```bash
fnpack create myapp --template docker
```

统一网关应用常用结构如下：

```text
myapp/
├── app/
│   ├── ui/
│   │   ├── config
│   │   └── images/
│   │       ├── icon_64.png
│   │       └── icon_256.png
│   └── docker/
│       └── docker-compose.yaml
├── cmd/
│   ├── main
│   ├── install_init
│   ├── install_callback
│   ├── upgrade_init
│   ├── upgrade_callback
│   ├── uninstall_init
│   ├── uninstall_callback
│   ├── config_init
│   └── config_callback
├── config/
│   ├── privilege
│   └── resource
├── wizard/
├── manifest
├── ICON.PNG
└── ICON_256.PNG
```

安装后主要目录为：

| 目录或变量 | 用途 |
| --- | --- |
| `TRIM_APPDEST` / `target` | 安装文件、运行资源和统一网关 Socket |
| `TRIM_PKGETC` / `etc` | 应用配置 |
| `TRIM_PKGVAR` / `var` | 重启后保留的运行数据和日志 |
| `TRIM_PKGTMP` / `tmp` | 临时文件 |
| `TRIM_PKGHOME` / `home` | 应用用户数据 |
| `shares` | `config/resource` 声明的共享目录 |

生命周期脚本和 Compose 文件应使用 `TRIM_*` 环境变量，不要硬编码 `/var/apps/myapp`、卷编号或用户目录。

## Manifest 模板

不暴露独立端口的统一网关应用可以使用：

```ini title="manifest"
appname=myapp
version=1.0.0
display_name=My App
desc=My fnOS application.
source=thirdparty
platform=all
maintainer=Your Name
maintainer_url=https://example.com
os_min_version=1.1.3102
desktop_uidir=ui
desktop_applaunchname=myapp.main
ctl_stop=true
checkport=false
```

注意：

- `appname` 是稳定的唯一标识，发布后不要随意更换；
- 第三方应用使用 `source=thirdparty`；
- 仅当包内不含架构相关二进制，并且使用的镜像也支持目标架构时，才使用 `platform=all`；
- 统一网关不使用 `service_port`，因此可以省略并设置 `checkport=false`；
- 长期运行的服务通常使用 `ctl_stop=true`；纯 CGI 静态包可以使用 `ctl_stop=false`；
- 不要为了省事设置 `install_type=root`，默认让用户选择应用存储位置。

完整字段见 [官方 Manifest 文档](https://developer.fnnas.com/docs/core-concepts/manifest/)。

## 最小权限

`config/privilege` 默认使用专用包用户：

```json title="config/privilege"
{
  "defaults": {
    "run-as": "package"
  },
  "username": "myapp",
  "groupname": "myapp"
}
```

仅在确实需要硬件设备时通过 `join-groups` 加入 `video`、`render` 等组。不要让长期运行、处理 Web 请求的服务以 root 身份运行。需要访问用户文件时，应通过资源声明和用户授权缩小范围，而不是授予 root。

`config/privilege` 约束 FPK 的原生脚本和进程，不会自动改变容器内用户。Docker 镜像还应单独配置非 root 用户和必要的文件权限。

## 注册桌面入口和统一网关

`app/ui/config`：

```json title="app/ui/config"
{
  ".url": {
    "myapp.main": {
      "title": "My App",
      "icon": "images/icon_{0}.png",
      "type": "iframe",
      "protocol": "",
      "gatewayPrefix": "/app/myapp",
      "gatewaySocket": "app.sock",
      "url": "/app/myapp/",
      "allUsers": true
    }
  }
}
```

字段规则：

- 入口 ID `myapp.main` 应以 `appname` 开头，并和 `desktop_applaunchname` 一致；
- `gatewayPrefix` 使用 `/app/{appname}` 或其稳定子路径，公开路径不要包含点号；
- `gatewaySocket` 只填写 `app.sock`，不要填写绝对路径；
- `url` 建议保留结尾 `/`，避免目录入口和相对资源出现两套 URL；
- 统一网关会忽略 `protocol` 和 `port`，`protocol` 保持空字符串即可；
- `iframe` 在 fnOS 桌面窗口内打开；需要完整浏览器环境时可改为 `url`；
- `allUsers=true` 表示所有已登录用户都能看到入口，不表示所有用户都拥有应用内的管理权限。

若入口只供管理员使用，应同时限制入口可见性，并在应用服务中检查管理员身份，不能只依赖桌面图标是否显示。

## 方案一：Docker FPK 通过 Unix Socket 接入

这不是“映射端口后添加一个快捷方式”。Docker 只是 FPK 内部的运行方式，安装、生命周期、入口、登录认证和访问路径仍由 fnOS 管理。

### 声明 Docker 项目

```json title="config/resource"
{
  "docker-project": {
    "projects": [
      {
        "name": "myapp",
        "path": "docker"
      }
    ]
  }
}
```

### Compose 模板

```yaml title="app/docker/docker-compose.yaml"
services:
  web:
    image: ghcr.io/example/myapp:1.0.0
    container_name: myapp-web
    restart: unless-stopped
    volumes:
      - "${TRIM_APPDEST}:/app/target:rw"
    environment:
      GATEWAY_SOCKET: /app/target/app.sock
```

关键点：

- 不写 `ports`，避免绕过 fnOS 认证并额外开放宿主机端口；
- 将 `TRIM_APPDEST` 以可写方式挂载到容器；
- 容器内服务监听 `/app/target/app.sock`；
- 宿主机对应 `/var/apps/myapp/target/app.sock`；
- 启动前只清理属于本应用的陈旧 Socket；停止时让进程正常退出；
- 不要为了省事把 Socket 长期设置为 `0666`，应在目标设备上验证网关所需的最小权限。

### Nginx 静态 SPA 示例

若镜像使用 Nginx，可以让 Nginx 直接监听 Unix Socket：

```nginx title="default.conf"
server {
    listen unix:/app/target/app.sock;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    location = /app/myapp {
        return 308 /app/myapp/;
    }

    location /app/myapp/ {
        rewrite ^/app/myapp/(.*)$ /$1 break;
        try_files $uri $uri/ /index.html;
    }
}
```

容器入口启动 Nginx 前应删除本应用上一次异常退出留下的 `app.sock`，否则绑定可能失败。删除目标必须是明确的应用 Socket 路径，不能使用宽泛目录或通配符。

如果后端服务原生支持 `--socket`、`--socket-path` 或类似选项，优先直接监听网关 Socket；如果服务只支持 TCP，可以在容器内增加一个受控的 Unix Socket 代理，但不要把内部 TCP 端口映射到宿主机。

### 运行状态

Docker 项目的启动和停止由 fnOS 根据 `docker-project` 资源处理。`cmd/main` 中的 `status` 仍应检查最能代表应用可用性的容器或进程：

- 运行返回 `0`；
- 未运行返回 `3`；
- 其他失败返回 `1`，并将可执行的错误信息写入 `TRIM_TEMP_LOGFILE`。

## 方案二：Native FPK 通过 Unix Socket 接入

Native 应用不需要 Docker。应用可以携带自己的 Go、Rust 或其他 Linux 二进制，也可以在 `manifest` 中声明官方运行时依赖，例如：

```ini
install_dep_apps=nodejs_v22
```

启动脚本将对应运行时加入 `PATH`，然后让服务监听：

```text
${TRIM_APPDEST}/app.sock
```

`cmd/main` 必须正确处理：

- `start`：幂等启动，拒绝重复进程，清理仅属于本应用的陈旧 Socket；
- `stop`：只停止记录并验证过的本应用进程；
- `status`：确认 PID 和实际进程身份，运行返回 `0`，未运行返回 `3`；
- 日志和 PID：写入 `TRIM_PKGVAR`，不要写入安装目录或系统目录。

不要仅凭一个可能被复用的 PID 执行 `kill`，也不要使用宽泛的 `pkill -f myapp`。完整运行时规则见 [官方运行时文档](https://developer.fnnas.com/docs/core-concepts/runtime/)。

## SPA 子路径适配

统一网关不会替前端修复根路径。应用公开地址是 `/app/myapp/` 时，构建产物、路由、插件、API 和 WebSocket 都必须认识这个前缀。

### Vite

```ts title="vite.config.ts"
import { defineConfig } from "vite";

export default defineConfig({
  base: "/app/myapp/",
});
```

也可以使用环境变量，让同一份代码同时支持根路径和 fnOS：

```ts
base: process.env.VITE_BASE || "/",
```

构建时：

```bash
VITE_BASE=/app/myapp/ npm run build
```

### React Router

```ts title="router.tsx"
const basename = import.meta.env.BASE_URL.replace(/\/$/, "");

export const router = createBrowserRouter(routes, { basename });
```

### 静态资源和接口

不要硬编码根路径：

```ts
const base = import.meta.env.BASE_URL;

fetch(`${base}api/session`);
fetch(`${base}plugins/index.json`);
```

WebSocket 应复用当前协议、主机和前缀：

```ts
const protocol = window.location.protocol === "https:" ? "wss:" : "ws:";
const socket = new WebSocket(
  `${protocol}//${window.location.host}${import.meta.env.BASE_URL}ws`,
);
```

同时检查 HTML 中的 `/favicon.svg`、`/config.js`，CSS 中的根路径资源，以及后端生成的重定向地址。对于无法配置 base path 的旧服务，可以在 Unix Socket 前增加路径重写代理。

## 登录态和业务鉴权

统一网关在转发前校验 fnOS 会话，并向应用服务发送：

| Header | 含义 | 示例 |
| --- | --- | --- |
| `X-Trim-Userid` | 当前用户 UID | `1000` |
| `X-Trim-Username` | 当前用户名 | `admin` |
| `X-Trim-Isadmin` | 是否为管理员 | `true` / `false` |

应用侧仍需执行自己的业务规则：

- 用户只能访问自己的记录和文件；
- 管理接口必须检查管理员身份；
- 查询记录时把当前 UID 纳入条件，不能只检查客户端传来的记录 ID；
- WebSocket 建立时把连接绑定到网关注入的 UID，不信任消息体中的用户 ID；
- 对文件路径进行规范化，拒绝 `..` 和越权目录。

只有当应用服务 **仅能通过统一网关 Socket 到达** 时，才能把这些 Header 作为可信身份上下文。若同时暴露 TCP 端口，客户端可以绕过网关并伪造同名 Header。

纯静态应用可以完全忽略这些 Header：fnOS 仍会阻止未登录用户访问页面。但请求 Header 不会自动出现在浏览器 JavaScript 中；若前端需要 UID 或用户名，应由受网关保护的后端提供会话接口。

### 浏览器本地数据

fnOS 登录隔离不会自动隔离 `localStorage`、IndexedDB 或浏览器缓存。v0.17.0 开发版已把画布、素材、媒体、生成记录、加密配置和 AI 任务移到后端，并按可信 UID 查询；浏览器只保留界面偏好、缓存、Canvas Agent 配置和一次性旧数据导入源。

需要严格多用户隔离时，应在获取可信 UID 后：

- 以 UID 为浏览器数据库或存储键命名空间；或
- 将业务数据移到服务端，并按 UID 做授权查询。

从独立端口迁移到统一网关后 Origin 会变化，旧端口下的浏览器数据也不会自动迁移。

## 统一网关与开放 API 的区别

统一网关解决“谁可以访问应用”和“当前请求来自哪个 fnOS 用户”。它不会自动授予应用读取 NAS 文件、打开系统页面或调用系统服务的权限。

需要这些能力时再接入 fnOS 开放 API：

- 在资源或 `api-scope` 中声明实际需要的能力；
- 前端使用官方 JS SDK；
- 后端使用 `TRIM_API_TOKEN`；
- 用户文件通过应用共享授权或用户个人授权获得；
- 后端使用文件 ACL 检查，不把路径本身当成授权证明。

参考 [官方开放 API 调用方式](https://developer.fnnas.com/api/calling/) 和 [授权与文件概览](https://developer.fnnas.com/api/authorization/overview/)。

## 打包、安装和更新

在应用项目目录执行：

```bash
fnpack build
```

生成 `.fpk` 后，可在 fnOS 应用中心中手动安装。脚本化测试可在设备上执行：

```bash
appcenter-cli install-fpk myapp.fpk
```

包含安装向导时：

```bash
appcenter-cli install-fpk myapp.fpk --env config.env
```

环境文件中的密码、Token 和密钥不得提交到仓库。`appcenter-cli` 需要设备上的相应管理权限；权限不足时使用管理员账号从应用中心手动安装，不要修改系统 RPC 或数据库权限。

更新应用时：

1. 提升 `manifest.version`；
2. 保持 `appname`、入口 ID、`gatewayPrefix`、Docker project name 和数据目录稳定；
3. 在 `upgrade_init` / `upgrade_callback` 中处理必要的数据或配置升级；
4. 重新执行 `fnpack build` 并安装新包；
5. 验证用户选择保留的数据没有被覆盖。

## 验收清单

- 应用中心能够正常安装、启动、停止、升级和卸载；
- fnOS 桌面图标能打开 `/app/myapp/`；
- HTTP、HTTPS 和计划支持的 FN Connect 入口都能访问；
- 未登录时请求被 fnOS 拦截；
- Docker Compose 没有宿主机 `ports` 映射；
- Socket 位于 `TRIM_APPDEST`，重启后能重新创建；
- SPA 刷新深层路由不会返回 404；
- 静态资源、API 和 WebSocket 都保留网关前缀；
- 普通用户不能调用管理员接口或访问其他用户数据；
- Native 进程默认以包用户运行，容器进程使用显式的非 root 用户，并且都只获得明确声明的资源；
- HTTPS 页面不会请求被浏览器拦截的 HTTP API；
- x86、ARM 和镜像架构声明与实际构建产物一致。

## 常见故障

| 现象 | 优先检查 |
| --- | --- |
| `/app/myapp` 返回 404 | fnOS 版本；`desktop_uidir`；入口 ID；`gatewayPrefix`；安装新包后是否重新注册入口 |
| 返回 502 或连接失败 | 服务是否运行；Socket 是否存在；Socket 路径和权限；是否残留旧 Socket |
| 首页可开但资源 404 | Vite/Webpack base path；HTML 根路径；Nginx rewrite；`url` 结尾 `/` |
| 刷新 SPA 子页面 404 | 服务端是否回退到 `index.html`；Router `basename` 是否正确 |
| WebSocket 失败 | 是否使用 `ws/wss`；是否保留 `/app/myapp` 前缀；代理是否处理 Upgrade |
| 登录后仍循环跳转 | 是否从 fnOS 当前域名入口访问；Cookie 域和协议是否一致；是否误用了独立端口 |
| Docker 端口可用但网关失败 | `TRIM_APPDEST` 是否可写挂载；容器是否真的创建了宿主机可见的 Socket |
| 用户之间看到相同本地数据 | IndexedDB/localStorage 是否按可信 UID 分区 |
| 外部 API 请求被浏览器拦截 | CORS 是否允许新的 fnOS Origin；HTTPS 页面是否请求 HTTP 资源 |

排查时先看应用运行状态和应用日志，再检查 Socket，不要直接编辑应用中心数据库或重启、替换 fnOS 系统网关配置。

## 无限画布适配要点

无限画布现在由 Vite SPA 和 Express 服务组成。画布、素材、媒体、生成记录、配置和全部 AI 模型调用均以服务端为准；浏览器只访问同源应用 API。后续制作 fnOS 包时推荐：

- 打成 Docker FPK，但取消宿主机 `3000:3000` 映射；
- 让 Express 通过 `SOCKET_PATH` 监听 `app.sock`，并由同一生产包提供前端静态资源；
- 使用 `/app/infinite-canvas/` 作为 Vite base 和 React Router basename；
- 修复 `/config.js`、`/plugins/index.json` 等根路径；
- 由管理员在后端配置共享 AI 渠道，继续禁止浏览器接收 Base URL 和凭据；
- 若通过 HTTPS 打开，确认本地 Canvas Agent 等明确保留的浏览器连接不会触发混合内容限制；
- 设置 `AUTH_MODE=fnos`，只信任统一网关注入的 `X-Trim-*` Header，不再额外暴露可伪造 Header 的 TCP 入口。
